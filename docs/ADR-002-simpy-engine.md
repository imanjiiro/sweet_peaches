ADR-002: Движок симуляции — SimPy, а не собственный event loop

Статус: принято

Контекст: ядро сервиса — это дискретно-событийная модель: пациенты
поступают в случайные моменты времени, занимают врачей как общий
ограниченный ресурс, освобождают их по окончании обслуживания. Такую
модель можно написать вручную (очередь событий + цикл обработки) или
взять готовую библиотеку для имитационного моделирования.

Варианты:
  1. Свой event loop на heapq — полный контроль над логикой, но нужно
     самим писать и тестировать очередь событий, генераторы процессов,
     синхронизацию ресурсов — то, что уже реализовано и проверено
     в существующих библиотеках.
  2. SimPy — готовая библиотека дискретно-событийного моделирования
     на Python с ресурсами (Resource, PriorityResource) из коробки.
  3. Тяжёлый фреймворк общего назначения (например, симуляционные
     инструменты вне Python-экосистемы) — избыточен для задачи такого
     масштаба и усложняет стек.

Решение: вариант 2. Прогон отделения строится как SimPy-процесс:
врачи — simpy.Resource/PriorityResource, пациенты — процессы,
поступающие по случайному расписанию.

Последствия: меньше своего кода и меньше рисков ошибок в базовой
механике очередей; но дизайн стратегий вынужден укладываться в модель
ресурсов SimPy — там, где это не получается напрямую (см. ADR-003),
нужны обходные решения поверх библиотеки.
