# Архитектура проекта Hospital Flow Simulation

## 1. Назначение и контекст

Система **Hospital Flow Simulation** предназначена для имитационного моделирования потоков пациентов в приёмном отделении больницы. Основная цель — оценка и сравнение различных алгоритмов и стратегий формирования очереди (FIFO, Priority, Dynamic Ageing) для минимизации среднего и максимального времени ожидания пациентов.

### Границы системы
* **Что делаем:** Приём параметров через веб-интерфейс и REST API, фоновое имитационное моделирование, расчёт статистических показателей (загрузка врачей, задержки пациентов), сохранение и отбражение результатов.
* **Чего сознательно не делаем:** Не интегрируемся с реальными медицинскими информационными системами (МИС), не обрабатываем персональные данные пациентов (ПДн), не строим трехмерную визуализацию приемного отделения.

## 2. Требования и ограничения
Ключевые требования:
    Обработка запросов на симуляцию без блокировки веб-сервера (асинхронное/фоновое выполнение).
    Наличие детерминированного ядра с возможностью воспроизведения результатов по заданному seed или списку пациентов.
    Наличие REST API с OpenAPI-документацией.
Ограничения:
    Стек: Python 3.11+, Django 5+, Django Ninja, SQLite.
    Однопроцессное окружение для учебного развертывания (фоновые задачи выполняются через threading.Thread).
    Качественные атрибуты:
Приоритет: Быстрота отклика UI (Responsive UI), точность и детерминированность математического ядра.
Пожертвовали: Горизонтальным масштабированием воркеров (на данном этапе Celery/Redis заменены на встроенные потоки).

## 3. Контейнеры (C4 уровень 2)
+-----------------------------------------------------------------------+
| Django Application Container                                          |
|                                                                       |
|  +-------------------+      +-------------------+                     |
|  | Web UI & API      | ---> | Task Service      |                     |
|  | (Views / Ninja)   |      | (web/services.py) |                     |
|  +-------------------+      +-------------------+                     |
|                                       |                               |
|                                       v                               |
|                             +-------------------+    +--------------+ |
|                             | Background Thread | -> | Core Solver  | |
|                             | (threading.Thread)|    | (core/)      | |
|                             +-------------------+    +--------------+ |
|                                       |                               |
+---------------------------------------|-------------------------------+
                                        v
                               +------------------+
                               | SQLite Database  |
                               +------------------+

Весь стек исполняется в рамках одного процесса Python: веб-интерфейс и API принимают запросы, передают задачи в сервис web/services.py, который запускает core/solver.py в отдельном фоновом потоке и сохраняет результат в БД SQLite.

## 4. Компоненты веб-приложения (C4 уровень 3, кратко)
Соблюдается строгое правило зависимостей:
    Веб-слой (web/views.py, web/api.py): Отвечает за обработку HTTP-запросов, валидацию входных данных через Django Forms / Pydantic и формирование ответов. Не содержит бизнес-логики расчёта.
    Сервисный слой (web/services.py): Управляет жизненным циклом задач (Task), связывает Django ORM и фоновые потоки исполнения.
    Вычислительное ядро (core/): Чистый Python без зависимостей от Django. Принимает параметры, проводит имитационное моделирование и возвращает словарь с результатами.

## 5. Модель данных
+-------------------------------------------------------+
|                         Task                          |
+-------------------------------------------------------+
| id            : AutoField (PK)                        |
| owner         : ForeignKey(User, null=True)           |
| name          : CharField(200)                        |
| params        : JSONField  -- doctors, rates, etc.    |
| status        : CharField(16) -- created, queued, ... |
| result        : JSONField  -- delays, utilization     |
| result_file   : FileField (null=True)                 |
| error         : TextField                             |
| core_version  : CharField(32)                         |
| created_at    : DateTimeField                         |
| finished_at   : DateTimeField (null=True)             |
+-------------------------------------------------------+
Результаты симуляций сохраняются прямо в поле result (JSONField) внутри записи Task, так как объём агрегированных метрик не превышает нескольких килобайт.

## 6. API
Автоматическая OpenAPI-документация доступна по адресу /api/docs.
Эндпоинты API
Метод	Путь	Код	Описание
POST	/api/tasks	202	Создать задачу симуляции и запустить в фоне
GET	/api/tasks/{id}	200 / 404	Получить полную информацию о задаче и её статусе
GET	/api/tasks/{id}/result	200 / 404	Получить только результаты завершенной задачи
GET	/api/tasks	200	Получить список всех задач

Диаграмма состояний задачи
[CREATED] ---> [QUEUED] ---> [RUNNING] ---> [DONE]
                                  |
                                  +---------> [FAILED]

## 7. Вычислительное ядро
Модуль: core/solver.py (или core/simulation.py).
Входные данные: Pydantic-схема SimulationParams (doctors, arrival_rate, service_mean, horizon_min, strategy, n_runs, patients).
Выходные данные: Pydantic-схема SimulationResult (avg_wait_time, max_wait_time, served_patients, doctor_utilization).
Корректность и эталон: Проверяется тестом core/tests/test_solver.py на 3 пациентах с ручным расчетом (среднее время ожидания = 5.0 мин).

## 8. Безопасность и доступ
Защита от перегрузок: Валидация входных данных ограничена сверху (например, arrival_rate и doctors скорректированы во избежание зависания потоков).
Секреты: Все секретные ключи (SECRET_KEY) загружаются через переменные окружения (.env).
Безопасность Git: Файлы кэша (__pycache__), виртуального окружения (.venv) и локальной базы данных (db.sqlite3) заблокированы в корневом .gitignore.

## 10. Эксплуатация
Логирование: Ошибки симуляции записываются в поле error соответствующей записи Task.
Типовые проблемы:
    Задача «зависает» в running: Возникает при сильном перегрузе системы (например, arrival_rate значительно превышает пропускную способность врачей). Решается корректировкой параметров формы на реалистичные.
    Блокировка базы SQLite: Фоновые потоки обязаны явно закрывать соединения с базой через connections.close_all().

## 12. Ретроспектива и использование AI
Что бы сделали иначе: С самого начала зафиксировали бы единые названия моделей в коде и документации, чтобы избежать путаницы между Task и SimulationRun.
Использование AI: AI-инструменты использовались для генерации шаблонов Pydantic-схем, написания unit-тестов и оформления документации.
Где AI ошибался:
    Предлагал слишком высокие дефолтные значения arrival_rate, вызвавшие 1000%+ перегрузку модели.
    Создавал .gitignore со строкой * внутри папки .venv, что блокировало отслеживание папки .github/.
    Разногласия в именовании моделей устранялись вручную и проверялись интеграционными тестами.
