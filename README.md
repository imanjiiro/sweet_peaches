# Hospital Flow Simulation

## Идея проекта

Моделируем поток пациентов в приёмном отделении больницы: как они
поступают, сколько ждут в очереди и как их обслуживают врачи. Задача —
сравнить разные стратегии распределения пациентов между врачами и
понять, какая из них даёт меньшее время ожидания при той же нагрузке.

## Как работает система

```
Пациенты поступают
        ↓
формируется очередь
        ↓
выбирается пациент по стратегии
        ↓
пациент обслуживается врачом
        ↓
собираются метрики
```

На текущем этапе ядро (`core/simulation.py`) полностью рабочее:
разбирает и заданный список пациентов (`patients`, для детерминированных
тестов), и умеет само сгенерировать поток по интенсивности и `seed`
(пуассоновские приходы + экспоненциальные времена приёма). Все три
стратегии — FIFO, Priority и Dynamic — реализованы. Расчёт запускается
и с формы `/`, и через API (`POST /api/tasks`), выполняется **в фоне**
(отдельным потоком) и не блокирует ответ — см. раздел «Фон и замер
времени» ниже.

## Входные данные

- количество врачей (`doctors`, 1..20);
- интенсивность поступления пациентов (`arrival_rate`, чел/мин);
- среднее время обслуживания одного пациента (`service_mean`, мин);
- длина смены (`horizon_min`, мин, по умолчанию 480 — 8 часов);
- сколько прогонов усреднить (`n_runs`, 1..1000);
- стратегия обслуживания (`strategy`).

`seed` на форме нет — это техническая деталь воспроизводимости,
сервис подбирает и сохраняет его сам (см. `web/services.execute_run`).

## Результат

- среднее время ожидания;
- максимальное время ожидания;
- средняя длина очереди;
- загрузка врачей;
- количество обслуженных пациентов.

## Стратегии

- **FIFO** — обслуживание в порядке поступления.
- **Priority** — сначала обслуживаются более срочные пациенты.
- **Dynamic** — приоритет учитывает и срочность, и время ожидания
  (аgeing: за каждые 15 минут ожидания приоритет растёт на единицу
  срочности — защита от «голодания» плановых пациентов при
  непрерывном потоке срочных).

## Фон и замер времени (galочка 7)

Расчёт (`core.simulation.simulate`) — тяжёлая функция: на плотном
потоке с несколькими прогонами счёт занимает секунды. Он выполняется
**в фоновом потоке** (`web/services.execute_run_async`,
`threading.Thread`), а не внутри HTTP-запроса — и форма `/`, и
`POST /api/tasks` отвечают сразу, не дожидаясь результата. Статус
прогона меняется `queued → running → done/failed` по ходу работы
потока — это видно, если обновить `/runs/` или повторно запросить
`GET /api/tasks/{id}` через долю секунды/секунду после создания.

Замер на большом входе (тот же прогон, что можно проверить командой
ниже):

```
doctors=5, arrival_rate=1.5, service_mean=6, horizon_min=480,
strategy=dynamic, n_runs=200, seed=1
→ 200 независимых прогонов, ~720 пациентов на прогон
→ время расчёта: 4.16 с (замерено time.perf_counter() вокруг
  core.simulation.simulate(); то же самое пишется в
  SimulationRun.duration_seconds при каждом реальном запуске)
```

Без фонового потока это была бы 4-секундная пауза на голом HTTP-запросе;
с ним пользователь получает ответ мгновенно, а результат смотрит
позже по статусу.

Это `threading.Thread`, а не полноценная очередь задач (Celery/RQ) —
для одно-процессного учебного проекта этого достаточно (см. ADR-001).
Единственная особенность: каждый поток открывает своё соединение к
БД и обязан закрыть его по завершении (`connections.close_all()`),
иначе соединения к SQLite будут копиться.

## Архитектура

```
Web/API  (web/views.py, web/api.py)
        ↓
Django models/forms  (web/models.py, web/forms.py)
        ↓
Core  (core/simulation.py)
        ↓
результаты симуляции
```

`core/` не зависит от Django и HTTP — это чистый Python, который можно
тестировать отдельно (`core/tests/`). Views и API не считают сами —
только сохраняют и читают данные через модели.

## Структура проекта

```
manage.py
config/            — настройки Django (settings, urls, wsgi/asgi)
core/              — вычислительное ядро, без Django
  simulation.py      — расчёт: заданный список пациентов ИЛИ случайная
                       генерация по arrival_rate/seed; FIFO/Priority/Dynamic
  tests/             — тесты ядра
web/               — Django-приложение
  models.py          — SimulationRun, SimulationResult
  forms.py, admin.py
  views.py           — HTML-страницы (не считают сами — зовут services.py)
  services.py        — связующий код: вызвать core, сохранить результат,
                       запустить расчёт в фоне (execute_run_async)
  api.py, schemas.py — JSON API (Django Ninja)
  tests/             — тесты API
  migrations/
  templates/web/
docs/
  idea.md, ER.md, fat_review.md
  adr/
```

## API

Django Ninja, автоматическая OpenAPI-документация — `/api/docs`.

| Метод | Путь | Код ответа | Описание |
|---|---|---|---|
| POST | `/api/tasks` | 202 | Создать задачу и запустить расчёт в фоне; отдаёт `task_id` сразу, статус обычно ещё `queued`/`running` |
| GET | `/api/tasks/{task_id}` | 200 / 404 | Задача целиком: параметры, статус, результат (`null`, пока не done) |
| GET | `/api/tasks/{task_id}/result` | 200 / 404 | Только результат (поля `null`, пока прогон не завершён) |
| GET | `/api/tasks` | 200 | Список всех задач |

## Web-интерфейс

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | форма запуска новой симуляции |
| POST | `/` | создать прогон (редирект на список) |
| GET | `/runs/` | список прогонов и их статусов |
| — | `/admin/` | админка Django |

## Быстрый запуск

```bash
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -r requirements.txt
cp .env.example .env

python manage.py migrate
python manage.py runserver
```

- Форма — http://127.0.0.1:8000/
- Список прогонов — http://127.0.0.1:8000/runs/
- API-документация — http://127.0.0.1:8000/api/docs
- Админка — http://127.0.0.1:8000/admin/ (после `createsuperuser`)

Тесты (включая эталонный тест ядра):

```bash
pytest
```

## Текущий статус

**Уже есть:**
- Django-каркас (`config/`, `web/`, `core/`);
- модели `SimulationRun` / `SimulationResult` и миграция;
- ER-диаграмма (соответствует текущим полям моделей);
- форма создания запуска + список запусков;
- API (4 эндпоинта, Django Ninja) с автодокументацией (`/api/docs`);
- ядро: разбор заданного списка пациентов **и** случайная генерация
  потока по интенсивности/seed, все три стратегии (FIFO/Priority/Dynamic);
- эталонный тест ядра (`core/tests/test_solver.py`) + тесты API
  (`web/tests/test_api.py`: 202/422/200);
- расчёт выполняется в фоне (`threading.Thread`), статус меняется
  `queued → running → done/failed`, время расчёта замеряется и
  сохраняется (`duration_seconds`);
- ADR-001 (выбор стека).

**Возможные дальнейшие шаги (не блокируют текущие галочки):**
- полноценная очередь задач (Celery/RQ) вместо `threading.Thread`,
  если проект выйдет за рамки одного процесса;
- реальная (не по формуле Литтла) средняя длина очереди — событийный
  учёт очереди во времени;
- график длины очереди во времени на странице результата.
