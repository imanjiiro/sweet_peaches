# ADR-001. Выбор стека: Django + Django Ninja

**Статус:** принято
**Дата:** 2026-09-03

## Контекст
Мы делаем веб-сервис для имитации очереди в приёмном отделении больницы. Нужно: вход пользователей и разделение задач по владельцам,
страницы с формой и результатом, REST API с документацией, хранение задач и результатов, фоновый запуск долгих расчётов.
Команда из трёх студентов, Python знаем на уровне курса, на проект около двух месяцев. Само ядро расчёта (`core/`) от веб-части не зависит,
поэтому выбор касается только оболочки вокруг него.

## Варианты
1. **Django + Django Ninja.** Пользователи, вход, админка, ORM и миграции есть сразу. Ninja добавляет API на pydantic-схемах (мы их уже
   пишем для ядра) и сам строит Swagger на `/api/docs`. Минусы: у Django много «негласных» правил (приложения, миграции, настройки),
   а Ninja моложе и о нём меньше примеров, чем о Django REST Framework.
2. **Django + Django REST Framework.** Тот же Django, но у DRF больше учебников и примеров. Минусы: сериализаторы DRF — ещё один способ описывать
   данные рядом с pydantic-схемами ядра, получилось бы две системы проверки входа.
3. **FastAPI + SQLAlchemy.** Лёгкий и быстрый, API и Swagger получаем сразу. Минусы: вход, админку, миграции (Alembic) и страницы пришлось бы
   собирать самим; на это ушла бы заметная часть времени, которое нужно ядру и тестам.
4. **Flask.** Самый простой старт. Минусы: всё из пункта 3 и при этом нет готовой документации API.

## Решение
Django + Django Ninja. Вход, регистрация, админка, миграции и проверка CSRF уже есть в Django, а те же pydantic-схемы, что проверяют вход ядра
(`core/schemas.py`), использует и API. Время тратим на расчёт, доступ к чужим задачам и тесты, а не на инфраструктуру.

## Чем платим
* Django ставит рамки: структура проекта, миграции при любой смене модели, настройки в `config/settings.py`. Приходится их учить.
* Django ORM по умолчанию работает с SQLite, а она плохо переносит одновременную запись из нескольких потоков: при пяти фоновых задачах сразу
  все падали с «database is locked». Лечится настройкой (`OPTIONS` в `config/settings.py`), но за это пришлось заплатить временем на поиск причины.
* Ninja меньше документирован: часть поведения (`auth=django_auth`, проверка CSRF в запросах `POST`) выяснили по исходникам и тестами.
* Для долгих расчётов в Django нет готового решения: сделали потоки (ADR-002) и очередь RQ как запасной режим.
