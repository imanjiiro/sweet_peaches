# ADR-002. Способ фоновой обработки: threading.Thread

**Статус:** принято
**Дата:** 2026-09-08

## Контекст
Вычислительное ядро симуляции при плотном потоке пациентов и нескольких прогонах (`n_runs`) выполняет расчёт в течение нескольких секунд. Выполнение вычислений синхронно внутри HTTP-запроса приводит к задержке ответа сервера, таймаутам и плоскому UX. Требуется асинхронная запуск-обработка задач без блокировки веб-сервера.

## Рассмотренные варианты
1. **threading.Thread (встроенные потоки Python)** — запуск расчета в фоновом потоке внутри процесса Django. Ответ уходит сразу (HTTP 202), задача создаётся со статусом `created`, поток переводит её в `running`, затем в `done` или `failed`.
2. **Celery + Redis** — промышленный стандарт очередей задач. Дает устойчивость, повторы и масштабирование; минус: требует поднятия сторонних сервисов (Redis/RabbitMQ), усложняет локальную разработку и развертывание команды.
3. **Django-Q2 / Huey** — очереди на базе ORM/SQLite. Проще Celery, но все равно требуют запуска отдельного процесса-воркера (`python manage.py qcluster`).

## Решение
Использовать **`threading.Thread`** (`web/services.py`: `create_task` запускает поток, `execute_task` выполняет расчёт). Для однопроцессного учебного проекта это избавляет от накладных расходов на инфраструктуру и внешние брокеры.

## Последствия
* Плюс: веб-интерфейс и API (`POST /api/tasks`) отвечают мгновенно, статус задачи отслеживается через polling.
* Риск / ограничение: потоки создаются с `daemon=True` и живут только внутри процесса Django. При перезапуске процесса (деплой, падение, Ctrl+C) поток **обрывается на полуслове, без исключения** — блок `except` в `execute_task` не выполняется. Задача, которая в этот момент была в статусе `running`, **навсегда остаётся «считается»**: статус `failed` не ставится, `finished_at` пустой, страница задачи опрашивает API бесконечно. Задачи в статусе `created` (поток ещё не успел стартовать) тоже не будут запущены заново.
* Что делать с этим: сейчас ничего не подбирает такие задачи, их нужно перезапускать руками. Варианты на будущее: при старте приложения переводить «зависшие» `running` в `failed` с пометкой «прервано перезапуском» либо перейти на очередь RQ + Redis (`USE_QUEUE=1`, `web/jobs.py`): задание переживёт перезапуск веб-процесса и его возьмёт воркер.
* Ограничение: потоки требуют явного закрытия соединений с SQLite (`connections.close_all()`) во избежание блокировок базы. Число одновременных потоков не ограничено.
* Случайные числа: в ядре у каждого расчёта свой генератор `random.Random(seed)` (`core/solver.py`, `generate_stochastic_patients`). Общий `random.seed` нельзя: два потока одновременно меняли бы его состояние, и один и тот же seed давал бы разные ответы.
