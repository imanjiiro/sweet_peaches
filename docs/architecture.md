# Архитектура проекта Hospital Flow Simulation

## 1. Назначение и контекст
Автор: Зузиева Айшат

Система **Hospital Flow Simulation** предназначена для имитационного моделирования потоков пациентов в приёмном отделении больницы. Основная цель — оценка и сравнение различных алгоритмов и стратегий формирования очереди (FIFO, Priority, Dynamic Ageing) для минимизации среднего и максимального времени ожидания пациентов.

### Границы системы
* **Что делаем:** Приём параметров через веб-интерфейс и REST API, фоновое имитационное моделирование, расчёт статистических показателей (загрузка врачей, задержки пациентов), сохранение и отбражение результатов.
* **Чего сознательно не делаем:** Не интегрируемся с реальными медицинскими информационными системами (МИС), не обрабатываем персональные данные пациентов (ПДн), не строим трехмерную визуализацию приемного отделения.

|  Пользователь /  | -------------------------> |    Hospital Flow Simulation       |
|  Исследователь   | <------------------------- | (Django Web, Ninja API, Core Engine) |
+------------------+                            +-----------------------------------+

## 2. Требования и ограничения
Автор: Зузиева Айшат

Ключевые требования:
    Обработка запросов на симуляцию без блокировки веб-сервера (асинхронное/фоновое выполнение).
    Наличие детерминированного ядра с возможностью воспроизведения результатов по заданному seed или списку пациентов.
    Наличие REST API с OpenAPI-документацией.
    Доступ только вошедшим пользователям и только к своим задачам (§8).
    Ограничение входных данных «не больше» до расчёта, чтобы один запрос не занимал сервер надолго (§7, §8).
Ограничения:
    Стек: Python 3.11+, Django 5+, Django Ninja, SQLite (в Docker — PostgreSQL).
    Однопроцессное окружение для учебного развертывания: по умолчанию фоновые задачи выполняются через threading.Thread; при USE_QUEUE=1 — через очередь RQ + Redis (ADR-002).
    Качественные атрибуты:
Приоритет: Быстрота отклика UI (Responsive UI), точность и детерминированность математического ядра.
Пожертвовали: Горизонтальным масштабированием воркеров в режиме по умолчанию (вместо Celery — встроенные потоки; очередь RQ + Redis включается флагом USE_QUEUE=1).

## 3. Контейнеры (C4 уровень 2)
Автор: Зузиева Айшат

+-----------------------------------------------------------------------+
| Django Application Container                                          |
|                                                                       |
|  +-------------------+      +-------------------+                     |
|  | Web UI & API      | ---> | Task Service      |                     |
|  | (Views / Ninja)   |      | (web/services.py) |                     |
|  +-------------------+      +-------------------+                     |
|                                       |                               |
|                                       v                               |
|                             +-------------------+    +--------------+ |
|                             | Background Thread | -> | Core Solver  | |
|                             | (threading.Thread)|    | (core/)      | |
|                             +-------------------+    +--------------+ |
|                                       |                               |
+---------------------------------------|-------------------------------+
                                        v
                               +------------------+
                               | SQLite Database  |
                               +------------------+

Весь стек исполняется в рамках одного процесса Python: веб-интерфейс и API принимают запросы, передают задачи в сервис web/services.py, который запускает core/solver.py в отдельном фоновом потоке и сохраняет результат в БД SQLite.

В Docker (`docker-compose.yml`) контейнеры другие: `web` (gunicorn), `worker` (RQ), `db` (PostgreSQL), `redis`; расчёт идёт через очередь (`USE_QUEUE=1`). Подробности — §9.

## 4. Компоненты веб-приложения (C4 уровень 3, кратко)
Автор: Зузиева Айшат

Соблюдается строгое правило зависимостей — кто кого вызывает: `web/views.py` и `api/api.py` → `web/services.py` → `core/`. Обратных вызовов нет.
    Веб-слой (web/views.py, api/api.py): Отвечает за обработку HTTP-запросов, вход и формирование ответов; ищет задачи только через сервис (`get_task`, `list_tasks`). Не содержит бизнес-логики расчёта. API — настоящий, на Django Ninja (`api/api.py`, адреса в `config/urls.py`); отдельной копии API в `web/` нет.
    Сервисный слой (web/services.py): Управляет жизненным циклом задач (Task), связывает Django ORM и фоновые потоки исполнения; здесь же правило «только свои» (`get_task`, `list_tasks`).
    Вычислительное ядро (core/): Чистый Python без зависимостей от Django. Принимает параметры, проверяет их схемой `core/schemas.py` (границы входа), проводит имитационное моделирование и возвращает словарь с результатами. Форма `web/forms.py` берёт границы из `core/schemas.py`, чтобы числа были в одном месте.

## 5. Модель данных
Автор: Умалатова Айна

+-------------------------------------------------------+
|                         Task                          |
+-------------------------------------------------------+
| id            : AutoField (PK)                        |
| owner         : ForeignKey(User, null=True)           |
| name          : CharField(200)                        |
| params        : JSONField  -- doctors, rates, etc.    |
| status        : CharField(16) -- created, queued, ... |
| result        : JSONField  -- delays, utilization     |
| result_file   : FileField (null=True)                 |
| error         : TextField                             |
| core_version  : CharField(32)                         |
| created_at    : DateTimeField                         |
| finished_at   : DateTimeField (null=True)             |
+-------------------------------------------------------+
Результаты симуляций сохраняются прямо в поле result (JSONField) внутри записи Task. Агрегированные метрики занимают доли килобайта, но вместе с ними хранится список wait_times — время ожидания каждого пациента первого прогона. При значениях формы по умолчанию это около 0,7 КБ, на верхней границе входа (10 пац/мин, смена 1440 мин, около 14 400 пациентов) — порядка 120–140 КБ (замер по ядру). Для одной записи это допустимо; для больших смен список стоит выносить в файл (поле result_file сейчас не используется). См. ADR-003.

## 6. API
Автор: Зузиева Айшат

Автоматическая OpenAPI-документация доступна по адресу /api/docs. Вход обязателен (auth=django_auth): без входа любой адрес отвечает 401. Подробно: docs/api.md.
Эндпоинты API
Метод	Путь	Код	Описание
POST	/api/tasks	202 / 401 / 403 / 422	Создать задачу симуляции и запустить в фоне; плохие параметры — 422
GET	/api/tasks/{id}	200 / 401 / 404	Статус задачи; чужая задача — 404, а не 403 (ADR-004)
GET	/api/tasks/{id}/result	200 / 401 / 404 / 409	Результат завершённой задачи; не готова — 409; чужая — 404
GET	/api/tasks	200 / 401	Список своих задач; без входа — 401

Диаграмма состояний задачи
Потоки (по умолчанию):  [CREATED] ---> [RUNNING] ---> [DONE]
                                          |
                                          +---------> [FAILED]

Очередь RQ (USE_QUEUE=1): [CREATED] ---> [QUEUED] ---> [RUNNING] ---> [DONE / FAILED]

## 7. Вычислительное ядро
Автор: Зузиева Айшат

Модуль: core/solver.py (контракт run(params: dict) -> dict); схемы входа и выхода — core/schemas.py.
Входные данные: Pydantic-схема SimulationParams (doctors, arrival_rate, service_mean, horizon_min, strategy, n_runs, seed, patients).
Выходные данные: Pydantic-схема SimulationResult (average_wait_time, max_wait_time, average_queue_length, doctor_utilization, served_patients_count, wait_times, core_version) и время расчёта elapsed_sec.
Граница входа (проверяется ДО расчёта, core/schemas.py): doctors не больше 20, arrival_rate не больше 10 пациентов в минуту, service_mean не больше 240 минут, horizon_min не больше 1440 минут (сутки), n_runs не больше 1000. Нарушение — 422, расчёт не начинается. Те же числа в форме (web/forms.py).
Случайность: у каждого расчёта свой генератор random.Random(seed), общий random.seed не используется — параллельные задачи не мешают друг другу (тесты test_same_seed_same_result, test_global_random_is_not_touched).
Очередь пациентов: куча heapq (выбор лучшего за log n шагов), общая сложность n·log n.
Средняя длина очереди: сумма времён ожидания всех пациентов, делённая на длину смены (max_time), то есть среднее число людей в очереди.
Корректность и эталоны (core/tests/test_solver.py), три эталона с известным ответом:
    1. test_reference_hospital_queue_fifo: 1 врач, 3 пациента в t = 0, приём по 5 мин — ожидания [0, 5, 10], среднее 5.0 мин (ручной расчёт).
    2. test_priority_differs_from_fifo: приём 10 и 2 мин; fifo даёт среднее 5.0, priority — 1.0 (ручной расчёт; сломаем приоритет — тест красный).
    3. test_average_queue_length_matches_queueing_theory: теория очередей M/M/1, 0,1 пац/мин, приём 5 мин, смена 1440 мин, 200 прогонов — Lq = 0,5, тест проверяет диапазон 0,4…0,6 (замер ядра: 0,50).
    Дополнительно: порядок кучи (test_priority_heap_order), неизвестная стратегия (test_invalid_strategy_rejected), границы входа (test_input_above_limit_rejected_before_calculation, test_input_at_limit_is_accepted).
Сколько считает (замер, README «Замер скорости»): один прогон на 19 170 пациентов — 0,06–0,07 с для всех стратегий (до перехода на heapq priority считал 21 с, dynamic — 42 с). Самый тяжёлый допустимый запрос (10 пац/мин, 1440 мин, 1000 прогонов) — около минуты (замер 02.10: 20 прогонов за 1,3–1,4 с, то есть 1000 прогонов — 65–70 с), поэтому расчёт идёт в фоне, см. ADR-002.

## 8. Безопасность и доступ
Автор: Умалатова Айна

Вход: страницы входа, выхода и регистрации — /login/, /logout/, /signup/ (web/urls.py, готовые представления Django, шаблоны в templates/registration/). Все страницы закрыты @login_required, API закрыт auth=django_auth (без входа — 401). Обычный пользователь входит так же, как админ, но без прав сотрудника.
Доступ «только свои»: задача всегда создаётся с владельцем (owner = request.user). Поиск идёт по номеру И владельцу (web/services.py: get_task, list_tasks); чужая задача — 404 и на странице, и в API (ADR-004), чужих в списке нет. Исключения для суперпользователя нет: ему — /admin/.
Защита от перегрузок: границы входа заданы в core/schemas.py (смена не больше 1440 минут, поток не больше 10 пациентов в минуту, приём не больше 240 минут, врачей не больше 20, прогонов не больше 1000, имя задачи в API до 200 символов). Нарушение — 422 с описанием ошибки (API) или ошибка поля (форма); расчёт не запускается.
Секреты и режим отладки: безопасно по умолчанию. DEBUG выключен (включается только строкой DEBUG=1 в .env), ключа в коде нет, SECRET_KEY берётся из .env (пример — .env.example). Без ключа проект не стартует (в режиме DEBUG=1 и в тестах ключ случайный). В docker-compose.yml ключ обязателен.
CSRF и XSS: во всех формах {% csrf_token %}, API с django_auth проверяет токен; пользовательский текст выводится через {{ }} без |safe.
Git: __pycache__, .venv, db.sqlite3, .env, *.log, media/ в .gitignore; 22 файла .pyc убраны из индекса (git rm -r --cached); .env не попадает и в образ Docker (.dockerignore).
Подробная проверка и список того, что не сделано: docs/security_review.md.

## 9. Развёртывание

Переменные окружения (.env, создаётся копированием .env.example; в git не попадает):
    SECRET_KEY=<длинный случайный ключ>

        source .venv/bin/activate

        py -m venv .venv
        .venv\Scripts\Activate.ps1
        pip install -r requirements.txt

        python manage.py runserver

## 10. Эксплуатация
Автор: Умалатова Айна

Логирование: Ошибки симуляции записываются в поле error соответствующей записи Task; сообщения сервера — в консоль runserver, в Docker — docker compose logs web worker.
Типовые проблемы:
    Задача «зависает» в running: Возникает при перезапуске процесса Django (фоновый поток обрывается, статус остаётся running — см. ADR-002) и при очень большом потоке пациентов, когда расчёт идёт долго. Задачу нужно создать заново; в первом случае помогает очередь RQ.
    Блокировка базы SQLite: Фоновые потоки обязаны явно закрывать соединения с базой через connections.close_all().
