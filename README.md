# Hospital Flow Simulation

Веб-сервис-симулятор работы приёмного отделения больницы: программа
моделирует поток пациентов, их ожидание и обслуживание врачами, а затем
**сравнивает разные стратегии распределения пациентов** по эффективности и
справедливости обслуживания.

## Идея

Пользователь задаёт параметры больницы: количество врачей, интенсивность
потока пациентов и среднее время обслуживания. Каждому пациенту случайным
образом присваивается один из трёх уровней срочности — **критический**,
**срочный**, **плановый**.

Сервис моделирует работу отделения при трёх стратегиях приёма пациентов:

- **FIFO** — обслуживание в порядке поступления;
- **приоритетная очередь** — сначала обслуживаются более срочные пациенты;
- **динамическая стратегия** — учитывает и срочность, и время ожидания.

Приоритетная стратегия быстрее обслуживает срочных пациентов, но может
приводить к **starvation** — слишком долгому ожиданию плановых пациентов.
Поэтому сравнение строится не только на скорости обслуживания, но и на
**справедливости распределения**.

Тяжёлая часть — не одиночный прогон, а сравнение стратегий: для каждой из
них нужно провести большое количество независимых симуляций, чтобы получить
статистически устойчивые метрики. Поэтому сравнение выполняется асинхронно,
в фоновой задаче.

Подробнее — в `docs/idea.md`.

### Метрики сравнения

Для каждой стратегии по результатам множества симуляций считаются:

- среднее и максимальное время ожидания;
- длина очереди;
- загрузка врачей;
- количество обслуженных пациентов;
- время ожидания пациентов разной срочности.

На основе этих метрик определяется, какая стратегия лучше подходит для
заданной нагрузки.

### Как работает

```
Параметры больницы
        ↓
Генерация пациентов (случайный поток и срочность)
        ↓
Выбор стратегии
        ↓
Симуляция работы врачей
        ↓
Сбор статистики
        ↓
Сравнение стратегий
        ↓
Результат
```

### Дополнительно — Level 2

Опциональное расширение: чрезвычайные ситуации во время симуляции —
резкий всплеск потока пациентов, временная недоступность врача, рост
среднего времени обслуживания. Позволяет определить, при какой нагрузке
отделение перестаёт справляться.

## Что нужно сделать (минимум)

### Что делаем

- Симулятор потока пациентов приёмного отделения с тремя уровнями
  срочности (критический / срочный / плановый).
- Три стратегии обслуживания: FIFO, приоритетная очередь, динамическая
  (срочность + время ожидания).
- Операция сравнения стратегий: много независимых прогонов на одних и тех
  же параметрах, сбор метрик, вывод о том, какая стратегия лучше для
  заданной нагрузки.
- Простой API поверх этой логики, чтобы параметры можно было передать
  снаружи, а результат — забрать в виде отчёта/графиков.

### Как делаем

1. **Генерация пациентов** — поток пациентов моделируется случайным
   процессом (интервалы между поступлениями), срочность присваивается
   случайно с заданными вероятностями.
2. **Очереди и врачи** — врачи представлены как ограниченный общий ресурс
   (`simpy.PriorityResource` / `simpy.Resource`); пациент занимает врача на
   случайное время обслуживания и освобождает его по завершении.
3. **Стратегии** реализуются как разные способы выбора следующего пациента
   из очереди:
   - FIFO — обычная очередь (`simpy.Resource`);
   - приоритетная — очередь с приоритетом по уровню срочности
     (`simpy.PriorityResource`);
   - динамическая — приоритет пересчитывается с учётом и срочности, и
     времени ожидания пациента (см. `ADR-003`, собственная очередь).
4. **Сбор статистики** — во время каждого прогона фиксируются время
   ожидания, длина очереди, загрузка врачей и т.д.
5. **Сравнение стратегий** — при одинаковых входных параметрах стратегии
   прогоняются N раз, метрики усредняются и сравниваются между собой;
   тяжёлый прогон выполняется в фоновой задаче, результат отдаётся по
   `task_id` (см. `ADR-001`).
6. **API** — тонкий слой над `core/`: принимает параметры, валидирует их,
   запускает симуляцию/сравнение, отдаёт статус и результат.

## API

| Метод | Путь | Код ответа | Описание |
|-------|------|------------|----------|
| POST | `/api/simulation/run` | 200 | Запустить одну симуляцию с заданными параметрами и стратегией |
| POST | `/api/simulation/compare` | 202 | Запустить фоновое сравнение всех стратегий |
| GET | `/api/tasks/{task_id}` | 200 / 404 | Статус фоновой задачи сравнения |
| GET | `/api/tasks/{task_id}/result` | 200 / 404 | Результаты сравнения стратегий и метрики |

Полное описание — в `docs/api.md`.

## Стек

Python 3.12, FastAPI, SimPy (имитационное моделирование очередей и
ресурсов, см. `ADR-002`), pydantic (валидация входных данных), matplotlib
(графики для сравнения стратегий), pytest (тесты логики симуляции),
ruff (линтер).

## Структура проекта

```
core/
├── patients.py     — генерация потока пациентов и срочности
├── strategies.py   — FIFO / приоритетная / динамическая стратегии
├── simulation.py   — один прогон симуляции (SimPy-модель отделения)
├── compare.py      — множественные прогоны + агрегация метрик
└── stats.py        — расчёт и оформление статистики

web/
├── schemas.py      — pydantic-схемы запросов и ответов
├── services.py     — единственная точка входа из API в core/
└── api.py          — эндпоинты FastAPI, фоновые задачи

docs/
├── idea.md         — подробное описание идеи и стратегий
├── api.md          — полное описание API
└── adr/            — архитектурные решения (ADR)
```

## Архитектурные принципы

- `core/` не зависит от FastAPI, БД и HTTP.
- Views и API не содержат бизнес-логики — только вызывают `web/services.py`.
- Вход валидируется pydantic-схемой до запуска симуляции. Никакого `eval`.
- Секреты — только в `.env`.

## Архитектурные решения (ADR)

Каждое «дорогое» архитектурное решение — отдельная страница в `docs/adr/`:
контекст, рассмотренные варианты, решение, последствия.

- `docs/adr/ADR-001-async-compare.md` — почему сравнение стратегий
  выполняется как фоновая задача, а не синхронный запрос.
- `docs/adr/ADR-002-simpy-engine.md` — почему в качестве движка симуляции
  выбран SimPy, а не собственный event loop.
- `docs/adr/ADR-003-dynamic-priority.md` — почему динамическая стратегия
  реализована собственной очередью, а не `simpy.PriorityResource`.
