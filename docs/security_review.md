# Проверка безопасности — 02.10.2026

Автор: Муцалова Иман

Проверено по коду и по `git ls-files`. Каждый пункт: что было, что сделали, как проверить.

## 1. DEBUG
Было: `DEBUG = os.environ.get("DEBUG", "1") == "1"` — без `.env` отладка включалась сама; в CI стояло `DEBUG: "True"` (код такое значение вообще не читает — включается только `1`).
Сделано: по умолчанию `DEBUG=0` (`config/settings.py`). Для своей машины `DEBUG=1` лежит в `.env.example`; в CI строку убрали. В `.env.example` и `docs/architecture.md` (§9) написано: на сервере 0.
Проверка: в `config/settings.py` значение по умолчанию — `"0"`; включается только строкой `DEBUG=1` в `.env`.

## 2. SECRET_KEY
Было: ключ записан прямо в коде (`"dev-only-insecure-key-change-me"`) и запасным значением в `docker-compose.yml` (`${SECRET_KEY:-dev-only-insecure-key}`).
Сделано: ключ только из окружения. Без `SECRET_KEY` проект не стартует (`ImproperlyConfigured`), кроме режима `DEBUG=1` и тестов (там случайный ключ на время процесса). В `docker-compose.yml` ключ обязателен (`${SECRET_KEY:?...}`).
Пароли в истории: поиск по `git log -p --all` нашёл только учебные заглушки (`dev-only-insecure-key...`, `POSTGRES_PASSWORD: calc` для локального docker, тестовые пароли `pass-a-12345` и т. п.). Ключ из истории считать недействительным: на сервере он не использовался.

## 3. Лишнее в git
Было: 22 служебных файла `__pycache__/*.pyc` лежали в индексе, хотя `.gitignore` их блокировал (добавлены до правила). Файлов `db.sqlite3`, `.env`, `*.log` в репозитории не было.
Сделано: `git rm -r --cached` на все `.pyc`; в `.gitignore` добавлены `*.log`, `media/`, `.pytest_cache/`, `.ruff_cache/`; добавлен `.dockerignore` (`.env`, `.git`, кэши не попадают в образ, иначе `.env` с `DEBUG=1` уехал бы в контейнер).
Проверка: `git ls-files | grep "\.pyc"` → пусто.

## 4. Границы входа
Было: предел длины смены (1440) стоял только в самописной копии API; в схеме ядра и в форме его не было, через форму проходило 48 000 минут (расчёт дольше минуты, сервер занят).
Сделано: границы заданы в `core/schemas.py` и проверяются ДО расчёта; форма берёт те же числа оттуда.

| Поле | Граница |
| --- | --- |
| `doctors` | не больше 20 |
| `arrival_rate` | не больше 10 пациентов в минуту |
| `service_mean` | не больше 240 минут |
| `horizon_min` | не больше 1440 минут |
| `n_runs` | не больше 1000 |
| имя задачи в API | от 1 до 200 символов |

Нарушение — 422 (API) или ошибка поля в форме; задача не создаётся. Самый тяжёлый допустимый запрос (10 пац/мин, 1440 мин, 1000 прогонов) считается около минуты в фоновом потоке (замер 02.10: 20 прогонов за 1,3–1,4 с, то есть 1000 прогонов — 65–70 с; ориентировочно).
Тесты: `core/tests/test_solver.py` (`test_input_above_limit_rejected_before_calculation`), `tests/test_api.py` (`test_horizon_min_validation_rejected`, `test_unknown_strategy_returns_422`), `tests/test_access.py` (`test_form_rejects_too_long_shift_before_calculation`).

## 5. Чужие задачи и вход
Было: страница отвечала на чужую задачу 403, API — 404; у суперпользователя было исключение только на странице; в самописной копии API была своя проверка входа, расходившаяся с настоящей.
Сделано: вход обязателен (`@login_required` на страницах, `auth=django_auth` в API — без входа 401); поиск по номеру И владельцу в `web/services.py` (`get_task`, `list_tasks`); чужая задача — 404 везде (ADR-004).
Тесты: `tests/test_access.py`, `tests/test_api.py`.

## 6. XSS
Пользовательский текст (название задачи, параметры, ошибка) выводится через `{{ }}` без `|safe` и `autoescape off`: поиск по `templates/`, `web/`, `api/`, `core/` совпадений не дал.

## 7. CSRF
Во всех четырёх формах (`base.html` — выход, вход, регистрация, новая задача) есть `{% csrf_token %}`; выход — только POST. API с `django_auth` проверяет CSRF-токен на запросах, меняющих данные: вошёл, но без токена — 403 (`tests/test_api.py`, `test_post_without_csrf_token_gets_403`).

## 8. Зависимости
Было: в `requirements.txt` версии диапазонами (`>=`): «у меня работает» сегодня и не работает у сокомандника через месяц.
Сделано: версии закреплены (`==`, проверено установкой и для Python 3.11 из CI). `pip-audit -r requirements.txt` (02.10) → «No known vulnerabilities found».
Проверка: `pip install pip-audit && pip-audit`. Нашлась дыра — поднять версию, прогнать `pytest`, закоммитить.

## Не сделано (честно)
* Регистрация (`/signup/`) открыта всем, без ограничения частоты; защиты от перебора пароля на `/login/` нет.
* `AUTH_PASSWORD_VALIDATORS` — только минимальная длина.
* Нет настроек для HTTPS (`SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`): нужны, когда сервис выставят в интернет.
* Число одновременных фоновых потоков не ограничено (см. ADR-002).
* В `docker-compose.yml` пароль базы `calc` — учебный, для локального запуска.
