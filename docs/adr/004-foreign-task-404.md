# ADR-004. Чужая задача — 404 (а не 403) и на странице, и в API

**Статус:** принято
**Дата:** 2026-10-02

## Контекст
Номер задачи — просто число в адресе (`/tasks/7/`, `/api/tasks/7`), номера идут подряд. Страница и API отвечали на чужую задачу по-разному: страница — 403 («запрещено»), API — 404 («не найдено»). Два правила для одного и того же: ответ 403 сообщает постороннему, что задача с таким номером есть, и перебором номеров можно узнать, сколько задач у системы. Кроме того, у страницы было исключение для суперпользователя, а в API его не было, и в самописной копии API была своя проверка входа, расходившаяся с настоящей.

## Рассмотренные варианты
1. **403 «доступ запрещён»** — честно говорит, в чём дело. Минус: подтверждает, что задача существует.
2. **404 «задача не найдена»** — для постороннего задачи №7 нет, так же как №999. Минус: пользователь, открывший чужую ссылку, не понимает, что дело в доступе.
3. **Оставить по-разному** (страница 403, API 404) — не требует правок, но правило не одно, и его легко сломать при изменении одного из мест.

## Решение
404 везде. Поиск по номеру И владельцу в одном месте — `web/services.py`: `get_task(user, task_id)` и `list_tasks(user)`; страница (`web/views.py`) и API (`api/api.py`) вызывают именно их. Вход обязателен: `@login_required` на страницах, `auth=django_auth` в API (без входа — 401). Исключение для суперпользователя убрано: ему — админка (`/admin/`).

## Последствия
* Плюс: одно правило в одном месте; номер чужой задачи ничего не выдаёт.
* Плюс: тесты проверяют и страницу, и API (`tests/test_access.py`, `tests/test_api.py`).
* Минус: пользователь, открывший чужую ссылку, видит «не найдено» и не понимает, что дело в доступе. Для учебного проекта это приемлемо.
* Минус: задачи без владельца (если такие остались в старой базе) никому не видны, посмотреть их можно только в админке.
