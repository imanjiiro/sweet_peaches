# ADR-003. Хранение входных параметров и результатов в JSONField

**Статус:** принято
**Дата:** 2026-09-12

## Контекст
Каждый прогон симуляции принимает сложный набор параметров (`doctors`, `arrival_rate`, `service_mean`, `strategy` и др.) и возвращает комплексный набор метрик (среднее и максимальное время ожидания, загрузка врачей, очереди). Необходима структура базы данных для хранения и отображения истории запусков.

## Рассмотренные варианты
1. **Хранение параметров и результатов в `JSONField`** внутри модели `Task` — гибкое хранение агрегированных метрик и параметров в виде JSON-структуры.
2. **Полная нормализация (отдельные таблицы `SimulationParam`, `SimulationMetric`, `DoctorStat`)** — классический реляционный подход.
3. **Сохранение результатов только в файловую систему (JSON/CSV)**, а в БД хранить лишь путь к файлу.

## Решение
Выбрать **`JSONField`** в модели `Task`. Позволяет быстро сохранять результаты вычислений ядра и Pydantic-схем без создания громоздких реляционных таблиц.

## Последствия
* Плюс: изменения в составе метрик ядра не требуют написания новых Django-миграций.
* Минус: сложные аналитические SQL-запросы по внутренним полям JSON в SQLite выполнять сложнее, чем по обычным колонкам (для текущих задач просмотра результатов через API/UI этого не требуется).
* Размер: агрегированные метрики занимают доли килобайта, но в `result` лежит и список `wait_times` (время ожидания каждого пациента первого прогона). При значениях формы по умолчанию (3 врача, 0,15 пац/мин, смена 480 мин) это около 0,7 КБ, а на верхней границе входа (10 пац/мин, смена 1440 мин, около 14 400 пациентов) — порядка 120–140 КБ. Для такого объёма JSONField в одной записи допустим; если границы входа расширять, большой список стоит выносить в файл (`Task.result_file`).
