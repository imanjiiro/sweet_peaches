# Анализ архитектурных проблем («Толстая» функция / Fat Service)

В исходном стартовом коде бизнес-логика, валидация и работа с БД смешаны в одном слое. Ниже описаны 5 ключевых проблем текущей реализации:

1. **Нарушение Single Responsibility Principle (SRP):** 
   Функция запуска симуляции одновременно отвечает за парсинг параметров, вызов ядра `solver.py`, запись результатов в БД и формирование HTTP-ответа.
   * *Решение:* Вынести бизнес-логику в слой сервисов (`web/services.py`), а представления (`views.py`) оставить только для приема запросов и возврата ответов.

2. **Прямая зависимость Core от веб-фреймворка:**
   Модуль симуляции напрямую завязан на Django-модели и форматы данных ORM, что делает невозможное использование ядра как отдельного CLI-инструмента или пакета.
   * *Решение:* Передавать в ядро чистые структуры данных (Python dict или Pydantic-схемы), изолировав `core/` от Django.

3. **Смешивание синхронных и тяжелых вычислений:**
   Расчёт симуляции выполняется прямо внутри HTTP-запроса (в веб-потоке). Если время расчета превысит несколько секунд, клиент получит таймаут (HTTP 504).
   * *Решение:* Вынести долгие вычисления в фоновые задачи (Celery / RQ) и менять статус `Task` асинхронно.

4. **Отсутствие чёткой схемы валидации на входе:**
   Параметры из формы или API читаются напрямую без жесткой проверки типов через Pydantic/Dataclasses на уровне сервисного слоя, что может привести к незаметным падениям внутри ядра.
   * *Решение:* Валидировать входные данные через Pydantic-схемы из `core/schemas.py` перед передачей в ядро.

5. **Неоптимальная запись больших объемов данных в БД:**
   Попытка сохранять детализацию по каждому пациенту поштучно или упаковывать многотысячные массивы в `JSONField` перегружает память и БД.
   * *Решение:* Использовать `bulk_create` для сохранения логов пациентов (`PatientLog`) или сохранять детализированные отчёты в `media/results/` в виде CSV/JSON файлов.
