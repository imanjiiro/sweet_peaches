# ADR-002. Способ фоновой обработки: threading.Thread

**Статус:** принято
**Дата:** 2026-09-08

## Контекст
Вычислительное ядро симуляции при плотном потоке пациентов и нескольких прогонах (`n_runs`) выполняет расчёт в течение нескольких секунд. Выполнение вычислений синхронно внутри HTTP-запроса приводит к задержке ответа сервера, таймаутам и плоскому UX. Требуется асинхронная запуск-обработка задач без блокировки веб-сервера.

## Рассмотренные варианты
1. **threading.Thread (встроенные потоки Python)** — запуск расчета в фоновом потоке внутри процесса Django. Задачи мгновенно получают статус `queued` и ответ HTTP 202.
2. **Celery + Redis** — промышленный стандарт очередей задач. Дает устойчивость, повторы и масштабирование; минус: требует поднятия сторонних сервисов (Redis/RabbitMQ), усложняет локальную разработку и развертывание команды.
3. **Django-Q2 / Huey** — очереди на базе ORM/SQLite. Проще Celery, но все равно требуют запуска отдельного процесса-воркера (`python manage.py qcluster`).

## Решение
Использовать **`threading.Thread`** (`web/services.execute_run_async`). Для однопроцессного учебного проекта это избавляет от накладных расходов на инфраструктуру и внешние брокеры.

## Последствия
* Плюс: веб-интерфейс и API (`POST /api/tasks`) отвечают мгновенно, статус задачи отслеживается через polling.
* Риск / ограничение: при перезапуске процесса Django незавершённые потоки завершатся с ошибкой; потоки требуют явного закрытия соединений с SQLite (`connections.close_all()`) во избежание блокировок базы.
